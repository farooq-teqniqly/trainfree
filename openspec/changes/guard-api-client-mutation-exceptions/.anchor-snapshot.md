# Add/Rename/Delete handlers in admin pages don't catch transport/parse exceptions

Raised during adversarial review of #50 (`add-category-library-crud`) -- see `docs/pr-reviews/PR_REVIEW_50.md`, finding "Minor [Pre-existing]" on `Categories.razor:168-225`. Confirmed as pre-existing on `Programs.razor` too, not a regression introduced by #50.

## Problem

`OnInitializedAsync` in both `Categories.razor` and `Programs.razor` explicitly catches `HttpRequestException`, `JsonException`, `InvalidOperationException`, `NotSupportedException`, and `OperationCanceledException` around the initial `GetXAsync()` call -- this is what stops a Cloudflare Access login-page response (or a network blip) from blanking the page.

`AddXAsync`, `RenameAsync`, and `DeleteAsync` in both pages call their respective API client methods (`CreateXAsync`/`RenameXAsync`/`DeleteXAsync`) with no such boundary. Those calls go through the same `HttpClient` and can throw the same exception types (transport failure, a redirected Access login page arriving as malformed JSON, cancellation), but nothing catches them -- the exception propagates out of the Blazor event handler instead of populating the page's existing `_addXError`/row `Error` state the way a typed `XFailed` outcome does.

Concrete trigger: a Cloudflare Access session expires between page load and clicking Save on an edit -- the outcome-based failure handling (`RenameCategoryFailed`, etc.) never fires because the exception happens before an outcome is ever returned.

## Direction

The cleanest fix is probably at the API-client layer, not per-page: `CategoriesApiClient`/`ProgramsApiClient`/`SessionsApiClient` could catch these exception types inside `CreateXAsync`/`RenameXAsync`/`DeleteXAsync` themselves and map them to the existing `XFailed` outcome (reusing the same fallback-message logic `ReadErrorAsync` already has for non-2xx responses), so every page gets the protection automatically instead of each page needing its own `try`/`catch` per handler. This is a natural fit for the shared `ApiClientBase` proposed in #51 -- worth designing together rather than as two separate changes.

## Acceptance

- [ ] A thrown transport/parse exception from `CreateXAsync`/`RenameXAsync`/`DeleteXAsync` results in the existing `XFailed`-outcome UI path (row/page error message), not an unhandled exception
- [ ] Covers all three current clients (Programs, Sessions, Categories) and whatever future ones land
- [ ] A test exists per client proving a thrown exception from the underlying `HttpClient` call surfaces as a `Failed` outcome rather than propagating

## Notes

Low priority -- not a regression, and the existing `ErrorBoundary` (see #22/#25) bounds the blast radius so a thrown exception here degrades the page rather than crashing the whole app. Best tackled alongside #51 since both touch the same three client classes.
