# Extract shared HTTP error-handling from the *ApiClient classes

Raised while reviewing SonarCloud findings on #50 (`add-category-library-crud`), which flagged a 42-line duplicated block between `CategoriesApiClient.cs`, `ProgramsApiClient.cs`, and `SessionsApiClient.cs` (26.9% file duplication density). Not a quality-gate blocker -- overall new-code duplication was 2.5%, under the 3% threshold -- but with a third client now shipped and at least a fourth (`ExercisesApiClient`, slice 6 of the roadmap) and likely more (slice 7's join-entity clients) still to come, the duplication only grows linearly with each new admin entity.

## Problem

`ProgramsApiClient`, `SessionsApiClient`, and `CategoriesApiClient` each independently define:

- The same `JsonSerializerOptions` (`PropertyNameCaseInsensitive = true`)
- An identical `ReadErrorAsync(HttpResponseMessage, CancellationToken)` (~42 lines): checks the response content-type is `application/json` before trying to parse it (guards against a Cloudflare Access HTML login page or other non-JSON failure response), reads an `ErrorDto`, and falls back to a generic `"Request failed with status {code}."` message while logging via a per-class `[LoggerMessage]` partial (`LogErrorBodyUnreadable`)
- The same shape of `CreateXOutcome`/`RenameXOutcome`/`DeleteXOutcome` success-vs-failure handling around each HTTP call
- A private `ErrorDto` record

None of this is entity-specific -- it is pure HTTP/JSON plumbing repeated per client.

## Direction (not prescriptive)

Something like a shared `internal abstract class ApiClientBase` (or a non-generic static/injectable helper) that owns `JsonOptions` and `ReadErrorAsync`, taking an `ILogger` instance so each concrete client keeps its own `ILogger<T>` for correct log categorization. The per-entity `[LoggerMessage]` declaration for `LogErrorBodyUnreadable` could plausibly become one shared, parameterized log method instead of one copy per client. Worth checking whether the create/rename/delete outcome-mapping boilerplate is similar enough to also share via a small generic helper, or whether that's better left per-client for readability.

## Acceptance

- [ ] `JsonOptions` and `ReadErrorAsync` (and its `ErrorDto`) exist in exactly one place, used by `ProgramsApiClient`, `SessionsApiClient`, and `CategoriesApiClient`
- [ ] Each client's own `ILogger<T>` category is preserved in the shared error-reading path (no loss of per-client log filtering)
- [ ] All existing `*ApiClientTests` (`ProgramsApiClientTests`, `SessionsApiClientTests`, `CategoriesApiClientTests`) keep passing unmodified in behavior (asserted outcomes/messages), even if their test setup changes
- [ ] SonarCloud's duplicated-lines-density finding on these files clears
