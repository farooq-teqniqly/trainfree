# listPrograms/listSessions/listCategories have no tiebreaker for creation-order ties

Raised during adversarial review of #50 (`add-category-library-crud`) -- see `docs/pr-reviews/PR_REVIEW_50.md`, finding "Minor [Pre-existing]" on `categories.js:11-15`. Confirmed as pre-existing in `programs.js`/`sessions.js` too, not a regression introduced by #50.

## Problem

`listPrograms`, `listSessions`, and `listCategories` all sort with `ORDER BY created_at ASC` only. `created_at` is an ISO-8601 string with millisecond resolution, set via `new Date().toISOString()` at insert time. Two rows created within the same millisecond (realistic for a fast double-click on an "Add" button before the row renders and disables the button, or two rapid Worker invocations) tie on that column, and SQLite gives no ordering guarantee between tied rows -- a list endpoint documented as returning rows "in creation order" can silently reorder them across two calls.

None of the three `spec.md` "creation order" scenarios/tests construct an actual tie, so this gap has no failing-test signal today.

## Fix

Add the table's `AUTOINCREMENT` `id` as a tiebreaker: `ORDER BY created_at ASC, id ASC` (sessions' query already has to qualify this as `sessions.id` per the existing comment in `sessions.js`, since `SELECT_COLUMNS` aliases `session_id AS id`). Apply to all three list functions together, since they're the same latent bug in three places.

## Acceptance

- [ ] `listPrograms`, `listSessions`, `listCategories` all tiebreak on the row's internal `id` when `created_at` matches
- [ ] A route-level test per table inserts (or creates) two rows with an identical `created_at` and asserts deterministic order

## Notes

Low priority -- no reported production symptom, and the fix is small and mechanical. Good candidate for a single focused PR touching all three files at once rather than fixing it piecemeal per future entity.
